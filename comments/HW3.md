# Модуль 3: Device Collector (с поддержкой шардирования через Apache ShardingSphere)

## Цель модуля
Разработать микросервис `device-collector-service`, который:

- получает сообщения о новых и изменённых устройствах из Kafka в формате Avro (валидация через Schema Registry),
- cохраняет/обновляет информацию о устройствах в PostgreSQL, используя шардирование через Apache ShardingSphere,
- Гарантирует идемпотентность, корректную обработку ошибок, экспортирует метрики.

## Архитектурные требования
### Компоненты
- Микросервис на Java 24 с использованием Spring Boot 3.5.
- Подключение к Apache Kafka (топик `devices`) с использованием Avro-десериализации и Schema Registry.
- Хранение данных об устройствах в PostgreSQL (таблица `devices`), доступ к базе через Apache ShardingSphere-JDBC для поддержки шардинга.
- Метрики и liveness/readiness через Spring Actuator.
- Тестирование и локальное окружение - через Testcontainers (Kafka, PostgreSQL, Schema Registry, ShardingSphere).

### Входной формат данных (Avro, топик `devices`)

```
{
    "type": "record",
    "name": "Device",
    "namespace": "com.nashkod.avro",
    "fields": [
        {"name": "deviceId", "type": "string"},
        {"name": "deviceType", "type": "string"},
        {"name": "createdAt", "type": "long"},
        {"name": "meta", "type": "string"}
    ]
}
```

### Структура хранения в PostgreSQL (шардинг)
**Таблица `devices`:**

**Колонка: device_id**
Тип: text
Описание: уникальный идентификатор устройства (PK)

**Колонка: device_type**
Тип: text
Описание: тип устройства

**Колонка: created_at**
Тип: bigint
Описание: время регистрации устройства (UNIX ms)

**Колонка: meta**
Тип: text
Описание: метаданные устройства

### Требования по шардированию:
- Все операции `insert/update/select` выполняются через Apache ShardingSphere, который распределяет данные по нескольким физическим схемам PostgreSQL на основе `device_id`.
- Шардинг настраивается по диапазону/хешу значения `device_id`.
- Миграции схемы и конфигурация шардинга оформляются в отдельные файлы (`yaml`/`xml`) и должны быть задокументированы в README.

### Оптимизация:
- Гарантировать идемпотентность через `ON CONFLICT (device_id) DO UPDATE`.
- Индекс по `device_id` на всех шардах для быстрой проверки и обновления.

## Функциональные требования
### Обработка устройств
- Подписка на Kafka-топик `devices`, получение сообщений в формате Avro.
- Валидация/десериализация через Schema Registry.
- Сохранение или обновление записей в PostgreSQL с обеспечением идемпотентности и маршрутизацией на нужный шард через ShardingSphere.
- Возможность горизонтального масштабирования.
### Обработка ошибок:
- При ошибке БД или недоступности шарда - retry с backoff, если неудачно N раз - отправка сообщения в Dead Letter Topic.
## Мониторинг
- Экспонирование стандартных метрик, healthcheck-эндпоинтов через Spring Actuator.
- Метрики количества успешно/неуспешно обработанных сообщений, ошибок по шардам.
## Нефункциональные требования
- Минимальная задержка обработки одного устройства (<100ms при стандартной нагрузке).
- Высокая отказоустойчивость (повторная обработка, DLQ при ошибках, автоматическое переключение на реплику в случае сбоя).
- Микросервис полностью автономен - разворачивается локально через docker-compose (Kafka, ShardingSphere, PostgreSQL, Schema Registry).
- Опционально: поддержка динамического добавления новых шардов без остановки основного сервиса (hot sharding).
## Тестирование
### Unit-тесты
- Десериализация Avro (с MockConsumer или Embedded Kafka).
- Проверка идемпотентности на уровне DAO/service.
- Тестирование корректности формирования shard-ключа и выбора шарда.
### Integration-тесты
- Проверка корректности записи и обновления в PostgreSQL через ShardingSphere (поиск по `device_id`).
- Проверка обработки ошибок (например, недоступность конкретного шарда, невалидные сообщения).
- Проверка публикации в Dead Letter Topic при превышении количества ошибок.
- Проверка работоспособности при масштабировании числа шардов (смена конфигурации ShardingSphere).
- Использование **Testcontainers** (Kafka + ShardingSphere + PostgreSQL + Schema Registry).

## Критерии приемки:

- Использование Spring for Apache Kafka с поддержкой Avro-десериализации и интеграцией со Schema Registry.
- Корректная интеграция с Apache ShardingSphere, все запросы к БД идут через слой шардинга.
- Гарантированная идемпотентность: запись и обновление устройств в PostgreSQL реализованы через `ON CONFLICT (device_id) DO UPDATE` или аналогичный механизм.
- Возможность масштабирования по партициям Kafka.
### Обработка ошибок и отказоустойчивость:
- Повторные попытки записи при ошибках БД или недоступности шарда.
- Корректная отправка сообщений в Dead Letter Topic при превышении лимита попыток.
- Логирование всех отказов и исключительных ситуаций с деталями по shard-ключу и шару.
### Интеграция метрик и healthcheck:
- Метрики по обработке, успехам, ошибкам (через Micrometer/Actuator), отдельные метрики по шардам.
- Корректные readiness/liveness-пробы для Kubernetes/Compose.
### Автоматизированное тестирование:
- Unit-тесты: логика обработки, идемпотентность, шардинг.
- Integration-тесты с Testcontainers (Kafka + ShardingSphere + PostgreSQL + Schema Registry).
- Покрытие автотестами не менее 90%.
### Документация
- README с инструкцией по запуску сервиса, описанием архитектуры, шардинга, обработки ошибок.
- C4-диаграммы: context, container и component (PlantUML).
- Sequence-диаграмма бизнес-процесса (PlantUML).

## Пример последовательности работы (PlantUML)
```
@startuml
actor KafkaBroker
participant "DeviceCollectorService" as DCS
participant "AvroDeserializer" as AVRO
participant "ShardingSphere JDBC" as SSJDBC
database "PostgreSQL Shard N" as PGN
participant "KafkaProducer (DLT)" as KP

KafkaBroker -> DCS : сообщение в Avro (Device)
DCS -> AVRO : десериализация Avro
AVRO --> DCS : Device DTO
DCS -> SSJDBC : сохранить/обновить устройство (по deviceId)
SSJDBC -> PGN : insert/update (шард определяется по deviceId)
alt ошибка сохранения/шардинга
DCS -> KP : отправить в Dead Letter Topic
end
DCS -> DCS : логирование, метрики, определение shard-ключа
@enduml
```

## Чеклист покрытия тестами для модуля: device-collector-service
### Интеграционные тесты (с Testcontainers)

- Поднятие Kafka и Schema Registry через Testcontainers.
- Публикация Avro-сообщения в топик Kafka (`devices`).
- Проверка, что сообщение успешно прочитано сервисом и десериализовано в DTO.
- Поднятие PostgreSQL с несколькими шардами и Apache ShardingSphere через Testcontainers.
- Проверка корректной маршрутизации INSERT/UPDATE операций по shard- ключу.
- Проверка корректного выполнения операции INSERT нового устройства через ShardingSphere.
- Проверка корректного выполнения операции UPDATE существующего устройства через ShardingSphere (идемпотентность).
- Проверка корректной обработки ошибки, если один из шардов недоступен (ожидается retry и/или отправка в DLT).
- Проверка отправки сообщений в Dead Letter Topic.
- Проверка корректного содержимого сообщения в DLT (исходный payload + метаданные об ошибке).
